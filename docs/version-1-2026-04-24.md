# Version 1（2026-04-24 更新）

**状态**: 开发中，本月冲刺上线
**目标**: 第一单（2999 工具包 + 可能的年付意向）完整跑通一次，客户反馈为"值"

---

## 一、这一版的战略节奏

**本月目标**:
1. **产品打磨到可以交付给真实客户**（不再是 demo，是能收钱的严肃版本）
2. **让第一单老板用起来**：今天可以通知他"基本上可以开始了"，下周跑通合同 + 打款 + 激活一整套
3. **不再扩展功能**（不再新增工具、不接 Stripe / 微信 / 支付宝 / Sentry / PostHog）

**核心交付物**:
- `pontai.cloud` 上线可访问
- 一条完整的 paperwork 链路：**pricing → 申请 → 审批 → 电子合同 → 签署 → 对公打款 → 激活 → 发票邮件 → 客户登录用工具**
- OCR 工具 MVP（DeepSeek + Anthropic 后处理）
- 合规的发票 + 对公合同

**本月不做**:
- Stripe / 微信支付 / 支付宝
- ICP 备案 / 阿里云任何东西
- SEO 工具 / 案例库扩展
- Sentry / PostHog / 其他观测性服务
- Google OAuth（只保留邮箱 OTP 登录）

### 2.2 代码与功能（90 个源文件，36 条路由，TS 全绿，Build 通过）

**核心框架**:
- Next.js 14 App Router + TypeScript strict
- Dockerfile + `railway.toml`（`output: 'standalone'`）
- Tailwind + Radix primitives + shadcn 风格的 UI 基础组件
- ESLint + Prettier + TypeScript strict

**数据层**:
- Drizzle ORM + Railway PostgreSQL
- 9 张核心表：`users / credit_balances / credit_transactions / tool_runs / files / leads / orders / contracts / payment_receipts`（+ `payment_events` 为 Stage 1/2 预留）
- Better Auth 的 `session / account / verification` 表已合入 schema
- Lazy DB Proxy（build 时不需要 DATABASE_URL 也能编译通过）

**认证**:
- Better Auth 邮箱 OTP（6 位验证码，Resend 发邮件）
- 中间件保护：`/account`、`/orders`、`/tools`、`/admin` 未登录自动跳 `/login`
- 基于 `ADMIN_EMAILS` 环境变量的管理员角色（首次邮箱匹配自动升级为 admin）

**Credits 系统**:
- `credit_balances` + `credit_transactions` append-only 流水模型
- 事务 + `SELECT ... FOR UPDATE` 行锁
- DB 层 CHECK: `available_credits >= 0`
- 核心函数：`grantCredits` / `consumeCredits` / `refundCredits` / `ensureWelcomeCreditsOnce`（注册送 50）

**营销页与申请流程**:
- `/` 首页
- `/pricing` 三档套餐展示（999 / 2999 / 36000，含早鸟价）
- `/pricing/apply` 申请表单（已登录预填 + 匿名提交都支持）
- `POST /api/leads` 写入 `leads` + 创建 `orders(draft)`
- Resend 自动发邮件通知 CTO（通过 `RESEND_ADMIN_EMAIL`）
- `/pricing/apply/success` 感谢页

**Admin 后台**:
- `/admin` 看板：新申请数 / 待审批 / 待签署 / 待对账 / 近 30 天激活
- `/admin/leads` 客户申请列表 + 状态筛选
- `/admin/leads/[id]` 单个申请的审批面板：
  - 调整价格、勾选早鸟
  - 一键"审批通过 + 生成合同"（调 Inngest 异步生成 PDF）
  - 预览合同 PDF
  - "发送给客户" → Resend 邮件 + 创建签署任务
  - 标记流失
- `/admin/orders` + `/admin/orders/[id]` 订单列表 + 对账 + 激活面板

**合同模板与 PDF**:
- 3 份 Markdown 合同模板：
  - [`consulting-999.md`](../src/lib/contracts/templates/consulting-999.md) — 信息化咨询服务协议（999 元）
  - [`saas-2999.md`](../src/lib/contracts/templates/saas-2999.md) — AI 工具 SaaS 订阅协议（2999 元）
  - [`annual-36000.md`](../src/lib/contracts/templates/annual-36000.md) — 年度服务协议（36000 元）
- Handlebars 变量替换（甲方信息、早鸟价、签署日期、对公账户等自动注入）
- `@react-pdf/renderer` 服务端 PDF 渲染 → R2 存储
- 异步 Inngest function 避免客户等待

**客户侧合同签署**:
- `/contracts/[id]` 客户预览 + 签署入口
- 嵌入 PDF iframe 预览
- 当前 `ESIGN_PROVIDER=stub` 模式下，客户点"我已阅读，确认签署"即视为签署成功
- `/api/webhooks/esign` 接收真实供应商回调（预留）

**对公打款 + 激活**:
- `/orders` 客户订单列表
- `/orders/[id]` 合同状态、对公账户信息（从环境变量读取）、订单号备注、进度条
- 可选上传打款回单（R2 presigned URL + `payment_receipts` 表）
- Admin 侧：对账 → 一键激活：
  - 自动创建账号（如果首次）或匹配现有用户
  - 写 `credit_transactions` + 更新 `credit_balances`（事务 + 行锁）
  - 生成增值税普通发票 PDF（3% 税率）→ R2 存储
  - Resend 发激活邮件 + 发票 PDF 附件

**第一个工具 OCR 发票识别**:

- `/api/tools/ocr-invoice/run` → 扣 5 credits → 触发 Inngest

- 前端轮询 `/api/tools/ocr-invoice/status`
- Prompt 模板：[`prompts/ocr-invoice-v1.md`](../prompts/ocr-invoice-v1.md)
- 失败自动退还 credits

**部署就绪**:

### 3.3 合同签署方案（已决策：本月 stub + 书面兜底）

**决策（2026-04-24）**: 第一单用 `ESIGN_PROVIDER=stub` 模式 + 线下书面兜底，不立即接电子签供应商。法大大和 e签宝都可接受，等 Stage 0 末期（第 3-5 单时）再接。

**stub 模式下的客户签约流程**:

```
客户在 /contracts/[id] 预览合同 PDF
    ↓
点"我已阅读，确认签署" → 系统标记 signed + 发打款邮件
    ↓
[书面兜底] 客户打印合同、手写签字、扫描或拍照回传
    ↓
[书面兜底] 我方打印合同、盖公章、扫描回传给客户
    ↓
双方签字/盖章扫描版邮件归档（和激活邮件一起）
```

**书面兜底为什么重要**（第一单是熟人关系，但必须留书面证据）:
- 出现争议时，双方手签的扫描 PDF 是直接证据
- 税务审计时要能拿出合同（电子版也行，但要能证明双方合意）
- 客户财务入账时通常要求看到合同扫描件

**产品侧建议的小动作**: 第一单时让老板把签字扫描件通过微信发你，你存到项目云盘里（`legal-archive/` 文件夹按年 / 按客户归档）。第 3 单开始再考虑在 `/contracts/[id]` 页面加一个"上传签字扫描件"按钮自动归档到 R2。

### 3.4 合同模板法务审阅（可选，第 3-5 单前做）

3 份合同模板是 CTO 草拟的业务逻辑版，**没有过法务**。考虑到:
- 变量注入后每个客户拿到的都是同一份底稿（"直接填入客户名字"）
- 第一单是熟人关系，退一步讲可以线下协商
- 花 1000-3000 元改一版可以终身复用

**建议触发时机**（任一满足即做）:
- 合同里发现漏洞（如客户要求改退款条款，你 case-by-case 改了 3 次以上）
- 即将签第 3-5 单（陌生客户进来）
- 有客户明确提出"能不能把合同版本给我法务看看"

**重点审查项**（找律师时照着说）:
- 退款条款边界（按比例还是全额，以什么为基准日）
- 知识产权归属（客户数据 vs 工具 IP，特别是 OCR 识别的发票）
- 违约责任和争议管辖地
- 保密条款期限和范围

### 3.5 电子签供应商切换（第 3-5 单时做）

接入步骤已经预留，参见 [`src/lib/providers/esign/`](../src/lib/providers/esign/)。**切到真实供应商时只改 3 处**:

1. `src/lib/providers/esign/` 新建 `fadada.ts` 或 `esignbao.ts`，实现 `IEsignProvider` 接口
2. `src/lib/providers/esign/index.ts` 加一个 case 分支
3. Railway 环境变量改 `ESIGN_PROVIDER=fadada`（或 `esignbao`），补充 `ESIGN_API_KEY` / `ESIGN_WEBHOOK_SECRET`

**选型参考**（任选一家，业务逻辑不变）:

| 选项 | 优势 | 劣势 | 费用参考 |
|------|------|------|---------|
| 法大大 | 企业认证较快，API 文档清晰 | 中小订单单价略高 | 企业版约 ¥3-5/份 |
| e签宝 | 国内市占率最高，司法存证完善 | 企业认证稍慢 | 企业版约 ¥3-5/份 |

**我的判断**: 法大大接入略快，e签宝生态更全。到时候你谁认识的销售好沟通就选谁，技术上没差别。

| 微信支付 / 支付宝 | 需要 ICP 备案 + 商户号 | Stage 2（月单 > 100 国内客户） |
| 阿里云任何服务 | Stage 0 不需要 | Stage 2 |
| ICP 备案 | Stage 0 不需要（`.cloud` 域名海外部署） | Stage 2 |
| 自建 Puppeteer | Stage 0 用托管 Browserless | Stage 1 |
| SEO 工具 | 聚焦 OCR 打磨 | Stage 1（Week 10+） |
| 客户自助修改合同 | 审批流程需要人工把关 | 不做 |
| 多角色审批（销售 → 法务 → CTO） | 就你一个人审 | 不做 |

## 七、风险与应对

| 风险 | 触发条件 | 应对 |
|------|---------|------|
| OCR 准确率上不去 80% | Week 2 测试失败 | 先用 Anthropic 单独做（不走 DeepSeek），或让客户上传更清晰的扫描件 |
| 老板要微信支付 / 支付宝 | 客户坚持不用对公 | 沟通合同专业度更高，不行就放弃这单不为特例改系统 |
| 合同纠纷 | 客户中途反悔 | 走合同退款条款，严格按日计算退款；保留对公流水留证 |
| Railway 挂了 | 可用率 < SLA | Railway 本身 SLA 99.9%，一年大概 8 小时停机；Stage 0 接受 |
| 法务审阅拖延 | 律师朋友忙 | 找法律文书代写（淘宝 500-1500 元快速改版） |
| 客户要专票 | 你是小规模纳税人 | 礼貌说明只能开普票，如果客户年单 > 3 万单独议 |
| DeepSeek / Anthropic 突然涨价或限额 | 外部依赖 | Provider 抽象层已经做好切换，真发生时 1-2 天换供应商 |
